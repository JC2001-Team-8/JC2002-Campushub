## 2. 12 条协作规则（全文）

### 规则 1：唯一真源

| 项 | 内容 |
| --- | --- |
| 内容 | 接口只认 `openapi.yaml`；结构只认 `schema.md` 与 `V1~V4`；规则只认 `rules.md` / `state-machines.md`；错误码只认 `error-codes.md`。前端类型、API Client、Mock、契约测试全部由 `openapi.yaml` 派生 |
| 禁止 | 代码硬编码路径而不引用生成物；在文档/群聊维护「接口清单副本」并据此开发；用 `/v3/api-docs` 反向覆盖契约；把「我以为的字段名」当依据 |
| 为什么 | 83 个 operationId 是 7 个人唯一能对齐的锚点；第二份定义必然漂移，且只在联调时暴露 |
| 检测方式 | PR 抽查字段名/枚举/错误码能否在 `schema.md` / `error-codes.md` 中 `grep` 到 |
| 违反后果 | 评审不通过；已合并的回退并登记 |

### 规则 2：三维边界锁定

| 项 | 内容 |
| --- | --- |
| 内容 | 每片可改范围由数据库表归属、Java 包路径归属、前端路由前缀归属三个维度共同锁定；开工前贴文件清单 |
| 禁止 | 只认领接口不认领表；跨片认领同一 Controller 类；两个切片共用同一前端路由前缀；以「只加一个字段」绕过清单 |
| 为什么 | 只按接口分工会出现「接口是我的、表是你的」，同一 Service 两拨人各写一半 |
| 检测方式 | 开工前清单经后端负责人确认；交棒时 `git diff --stat` 与清单逐条比对 |
| 违反后果 | 清单外文件视为越界，撤回改动并登记 |

### 规则 3：禁止越界（含禁止依赖他片 `ServiceImpl`）

| 项 | 内容 |
| --- | --- |
| 内容 | 只写本片归属文件；跨片调用**只能依赖对方 Service 接口或公开仓储方法**，禁止依赖 `ServiceImpl`；需要他片改动走「提需求 → 归属片实现 → 交回」 |
| 禁止 | 改他片 Controller/Service/ServiceImpl/Repository/Entity；直接 `INSERT/UPDATE/DELETE` 他片独占表（E-01~E-10 登记的受限写除外）；`import` 他片 `service.impl`；反射或原生 SQL 绕过接口 |
| 为什么 | 依赖实现类会把两片焊死；越界改动不立刻报错，但会破坏「谁改了这行」的可追溯性 |
| 检测方式 | PR 审查第 6 项：是否引用他片 `ServiceImpl` 或独占表；`git diff --stat` 比对 |
| 违反后果 | 撤回越界改动，把需求写成缺陷单交归属片 |

### 规则 4：公共实体只读

| 项 | 内容 |
| --- | --- |
| 内容 | `User`、`TradeZone`、`Category`、`ItemCondition`、`PickupPoint`、`Notification` 六个公共实体由**切片 1 建立**，自切片 2 起只读；各片只能查询与引用 |
| 禁止 | 业务代码 `save()` 公共实体；业务迁移 `INSERT/UPDATE` 字典表；为测试在业务代码造字典数据；Service 内缓存后回写 |
| 为什么 | 6 个实体被四个切片引用，任何改动同时影响他片，必须收敛到单一所有者 |
| 检测方式 | 代码审查检索公共实体的写操作；迁移审查字典表写入 |
| 违反后果 | 撤回改动；确需变更由切片 1 走 `V5+` 与审批 |

> 已登记例外：`users` 的封禁/解封由切片 4 受限写（E-07）；`notifications` 写入实现归切片 4（E-10）。

### 规则 5：交接规则（切片闭合才交棒）

| 项 | 内容 |
| --- | --- |
| 内容 | 切片必须达到闭合状态才可交棒；闭合判定为第 4 章 10 项交接清单逐项打勾，并由下一片负责人审查、验收人核验签字 |
| 禁止 | 「代码写完但没测」就宣布闭合；用口头说明替代文档留痕；跳片；边交棒边改上一片代码 |
| 为什么 | 串行接力是对抗并行冲突的核心；未闭合就交棒会同时出现两片改公共文件，主干带病 |
| 检测方式 | 闭合现场执行构建、健康检查、冒烟脚本、哈希与 diff 核对（见 `EXECUTION-CHECKLIST.md`） |
| 违反后果 | 交棒不生效；阻塞项必须本片解决或把 operationId 移出并登记 |

### 规则 6：Git 规则

| 项 | 内容 |
| --- | --- |
| 内容 | 每人用自己的 GitHub 账号；分支 `feat/slice<N>-<简短描述>`；PR + 至少 1 人评审；提交信息 `feat(切片名): 具体内容`；每天至少提交一次可编译状态 |
| 禁止 | 共用账号或代提交；`git push --force`；`git reset --hard`；`git checkout --` 丢弃他人改动；一次性提交上千行；提交 `target/`、`.mvnrepo/`、`.DS_Store`、IDE 配置 |
| 为什么 | 贡献可见与问题回溯都依赖「这行是谁在哪个切片写的」；大提交让评审走过场 |
| 检测方式 | 提交作者分布；PR 行数；`git log` 与 `git diff --stat` |
| 违反后果 | 拒绝合并；已合并的回退并登记 |

### 规则 7：契约变更

| 项 | 内容 |
| --- | --- |
| 内容 | 任何契约变更走 [`../docs/iteration1/design/api-freeze.md`](../docs/iteration1/design/api-freeze.md) **§4**：申请 → 影响面评估 → 类型判定 → 审批 → 更新并升版 → 台账 → 前后端同步 |
| 禁止 | 私改 `openapi.yaml`；新增 endpoint（2026-10-09 后；**P0 例外按 `api-freeze.md` §4 由接口契约负责人 + 需求方 + 后端负责人三人审批，未审批前仍属禁止**）；破坏性变更（删字段、改类型、可选改必填、改路径）；先用后补 |
| 为什么 | 契约一改，生成物、Mock、测试、前端类型全部作废，必须有人承担影响面成本 |
| 检测方式 | `openapi.yaml` 哈希前 16 位 `36bd7a03a184734c`；PR 是否含契约文件 |
| 违反后果 | 拒绝合并；无台账的契约改动直接回退 |

### 规则 8：数据库迁移

| 项 | 内容 |
| --- | --- |
| 内容 | `V1`~`V4` 已冻结、只读；任何结构变更新增 `V5+`，必须增量、可重复部署；新增前在空库顺序验证 `V1` 到最新版全部成功 |
| 禁止 | 修改已应用脚本（含注释、空白、换行）；删除迁移文件；业务代码用 DDL 建表/改列；`V3` 用于生产；改 `V4` 已重建的 `idx_orders_review_window` 条件 |
| 为什么 | Flyway checksum 不匹配会让全组无法启动，是「一人失误、全组阻塞」点 |
| 检测方式 | 4 个迁移哈希与 `HANDOVER` 基线一致；PR 是否新增 `V5+` |
| 违反后果 | 立即上报；不得删库重来；按归属片提出新迁移 |

### 规则 9：错误处理

| 项 | 内容 |
| --- | --- |
| 内容 | 所有错误返回 `error-codes.md` 已登记的 93 个码之一；失败用 `ErrorResponse`（`code`/`message`/`details`/`traceId`/`timestamp`）；前端按 `details[].field` 定位字段 |
| 禁止 | 自造错误码；裸 500；用 200 包装失败（契约约定的幂等语义除外，如 `REPORT_ALREADY_EXISTS` 返回 200）；改命名风格 |
| 为什么 | 93 个码覆盖 E-01~E-17；临时发明会让前端无法预先处理，体系很快失效 |
| 检测方式 | PR 随机抽 3 个错误码在 `error-codes.md` 检索 |
| 违反后果 | 评审不通过；新增错误码必须走规则 7 |

### 规则 10：越权规则

| 项 | 内容 |
| --- | --- |
| 内容 | Controller 层声明权限（`@PreAuthorize`），Service 层做归属校验，**两层都要有**；权限依据契约 `security` / `x-required-roles` 与 `api-permission-mapping.md`；越权一律 **403** |
| 禁止 | 只靠前端隐藏按钮；只做 Controller 校验；非本人资源返回 404；管理员参与交易；用「资源不存在」代替「无权访问」 |
| 为什么 | 前端隐藏不构成安全边界；只做 Controller 会漏掉服务内部调用；E-02 明确要求 403 |
| 检测方式 | 越权用例：他人资源 / 非管理员 / 未登录 / 被处罚用户四类 |
| 违反后果 | 评审不通过；已合并的回退 |

### 规则 11：幂等与并发（含占用与投影同事务）

| 项 | 内容 |
| --- | --- |
| 内容 | 两层防护缺一不可：**幂等键**防重复提交 + **条件更新/乐观锁**防并发竞争；16 个必填幂等接口必须校验 `Idempotency-Key`；**写占用台账与改写商品状态必须同一事务** |
| 禁止 | 「先查询、再判断、后无条件更新」；必填接口忽略幂等键；把 `acceptSwapProposal` / `counterSwapProposal` 的第二次调用当幂等成功（IDEM-B 必须明确失败）；拆开占用与投影；信任前端剩余时间 |
| 为什么 | 并发窗口只在真实并发下暴露；「不卖超」「不重复占用」「不出现一半被占住」是核心承诺 |
| 检测方式 | 并发用例 ≥ 2 并发；16 个必填接口逐一幂等用例；审查条件更新语句与事务边界 |
| 违反后果 | 评审不通过；并发用例失败不得交棒 |

### 规则 12：代码审查

| 项 | 内容 |
| --- | --- |
| 内容 | 每个 PR 至少 1 人评审；交棒审查由下一片负责人执行，做 6 项合规检查（越界 / 契约一致 / 条件更新与同事务 / 错误码 / 测试 / 跨片依赖） |
| 禁止 | 自审自过；评审未通过就合并；以赶进度跳过；把「AI 生成」当免审理由；下一片负责人直接替上一片改代码 |
| 为什么 | 下一片最有动机认真审：上一片的越界与偷工最后都变成他的成本 |
| 检测方式 | PR 评审记录逐项结论；6 项清单见 `EXECUTION-CHECKLIST.md` |
| 违反后果 | PR 不合并；责任人按红线处理 |

## 3. 6 条红线（全文）

### 红线 1：禁止一人包干一个迭代

| 项 | 内容 |
| --- | --- |
| 表现 | 某个人把整片的表、后端、前端全部写完，其他人无从参与 |
| 为什么禁止 | 贡献不可见；单点故障；无人能评审；迭代一的单人假设会被固化 |
| 正确做法 | 每片至少 1 后端主办 + 1 后端协办 + 1 前端主办；协办可跨片复用 |
| 检测方式 | PR 提交者分布；某片 90% 以上提交来自同一人即复核 |

### 红线 2：禁止并行修改同一文件或同一模块

| 项 | 内容 |
| --- | --- |
| 表现 | 两分支同时改同一 Controller/Service/Entity，或同时改公共层（`ApiResponse`、`ErrorCode`、`GlobalExceptionHandler`、`SecurityConfig`） |
| 为什么禁止 | 冲突需人工判断语义，解错不会让测试变红，只会让行为悄悄改变 |
| 正确做法 | 公共层在切片 1 定型；后续走「提需求 → 所有者改」；同片按 operationId 或类划分文件级归属 |
| 检测方式 | 合并前 `git diff --name-only`；同一文件同一时间窗被两分支修改则先合并一方 |

### 红线 3：禁止未经评审修改契约或迁移脚本

| 项 | 内容 |
| --- | --- |
| 表现 | 直接编辑 `openapi.yaml` 的字段/枚举/错误码；直接编辑 `V1`~`V4` |
| 为什么禁止 | 契约改动让前后端同时返工；迁移改动让全组无法启动 |
| 正确做法 | 契约走 `api-freeze.md` §4；迁移新增 `V5+` |
| 检测方式 | 合并前核对 `openapi.yaml` 与 4 个迁移哈希；不一致且无台账即拒绝合并 |

### 红线 4：禁止 AI 生成代码后不跑本地测试就提交

| 项 | 内容 |
| --- | --- |
| 表现 | 把 AI 生成的 Service 直接提交，理由是「看起来对」 |
| 为什么禁止 | AI 会用合理字段名填充没读到的细节，编译期不报错，运行时才暴露 |
| 正确做法 | 提交前至少 `mvn clean package -DskipTests` + 本片自测；字段/枚举/错误码都能 `grep` 到源头 |
| 检测方式 | 随机抽 3 个字段名/枚举值/错误码，在 `schema.md` 与 `error-codes.md` 检索，全部命中才通过 |

### 红线 5：禁止用同一个 GitHub 账号代替多人提交

| 项 | 内容 |
| --- | --- |
| 表现 | 全组共用一个账号，或一人代他人提交 |
| 为什么禁止 | 直接违反「GitHub 贡献可见」；工作量、缺陷归因、评审记录全部失效 |
| 正确做法 | 每人配置自己的账号与 SSH key；提交前 `git config user.name/email` 自检 |
| 检测方式 | 提交作者分布；某片只有 1 个作者但声称多人参与即复核 |

### 红线 6：禁止在交接时留下未通过的测试或未解决的编译错误

| 项 | 内容 |
| --- | --- |
| 表现 | 「这一片先交，测试下片再补」「这个编译错误是别人的文件导致的」 |
| 为什么禁止 | 串行接力前提是主干干净；带病主干会让下一片无法区分「我引入的问题」和「继承的问题」 |
| 正确做法 | 未解决问题显式登记并说明是否阻塞；阻塞项本片解决，或把 operationId 移出并登记 |
| 检测方式 | 闭合现场 `mvn clean package -DskipTests` + 本片冒烟脚本，失败即不通过 |

| 9 | 下一片负责人已完成代码审查 | 6 项合规检查逐项通过 | 审查记录 | 下一片负责人 | [ ] |
| 10 | 口头交接已完成 | 能复述本片交付、遗留、受限写 | 交接会议记录 | 后端主办 + 下一片负责人 | [ ] |

**未勾选处置**：① 本片内解决后重走清单；② 把对应 operationId 移出并登记（原因 + 影响）。**不允许「带病交棒 + 口头保证下片补」。**

## 5. Git 日常规范

```bash
# 每天开工先拉主干
git checkout main
git pull --ff-only

# 切到本片分支
git checkout feat/slice2-item-publish
git rebase origin/main

# 提交前自检是否越界
git status --short
git diff --stat
git diff --name-only

# 确认提交身份（红线 5）
git config user.name
git config user.email

# 提交与推送
git add <本片文件>
git commit -m "feat(切片2): 实现 createItem 与 uploadImage（R-10/R-12/R-03）"
git push -u origin feat/slice2-item-publish
```

**禁止命令**

| 命令 | 原因 |
| --- | --- |
| `git push --force` | 覆盖他人提交，不可逆 |
| `git reset --hard` | 丢弃本地与他人可见改动 |
| `git checkout --`（用于丢弃改动） | 无提示丢弃改动 |
| `git add -A` 无差别暂存 | 易带入敏感/构建文件 |

## 6. 常见问题（Q1~Q5 全文）

### Q1：前人 Bug 怎么办

| 项 | 内容 |
| --- | --- |
| 场景 | 切片 3 发现切片 1 的 `getPublicProfile` 头像字段与前端约定不一致 |
| 处理步骤 | ① 先分类：契约错还是实现错；② 实现错 → 不在本片直接改，写缺陷单（切片 / operationId / 复现 / 期望）交归属片；③ 契约错 → 停手走 `api-freeze.md` §4；④ 阻塞进度时先按契约实现并登记「依赖上游修复」，验收项标记「待上游修复后复验」 |
| 禁止 | 顺手改上游代码；不通知上游就改契约；在前端硬编码绕过 |
| 为什么 | 「顺手改」让责任链断裂；绕过会在上游修复后产生双重修正 |

### Q2：发现契约缺少接口怎么办

| 项 | 内容 |
| --- | --- |
| 场景 | 实现交换流程时发现需要「查询可接受提议数量」，但 83 个 operationId 里没有 |
| 处理步骤 | ① 先自查既有接口能否承载（如用 `listSwapProposals` 分页、`getUnreadNotificationCount`）；② 确需新增按类型 F 提交变更申请；③ 三人审批（接口契约负责人 + 需求方 + 后端负责人）；④ 通过后由接口契约负责人更新契约、升版、登记台账 |
| 禁止 | 先用后补；多返回一个字段当临时方案不登记；以「就差一个接口」施压 |
| 为什么 | 2026-10-09 后不允许新增接口是冻结核心；放宽一次，83 就不再是可靠坐标 |

### Q3：AI 生成的代码不符合契约怎么办

| 项 | 内容 |
| --- | --- |
| 场景 | AI 把 `priceDisclaimer` 写成 `disclaimer`，或把 `ACCEPTING` 写成 `ACCEPT` |
| 处理步骤 | ① 以契约改代码；② 把契约片段直接喂给 AI 重写；③ 逐项核对字段名、类型、required、枚举、金额格式、时间格式；④ 把该类错误加入本片核对清单；⑤ 提交前跑本地测试 |
| 禁止 | 为迁就 AI 改契约；只做「能编译」的核对；不核对就提交 |
| 为什么 | AI 的错误集中在「没读到但必须填」的细节，编译期不报错 |

### Q4：本地跑不通怎么办

| 项 | 内容 |
| --- | --- |
| 场景 | `docker compose` 起不来或端口冲突 |
| 处理步骤 | ① 看端口（5432 占用可改 `POSTGRES_HOST_PORT`）；② 看健康（等 postgres healthy）；③ 看迁移（checksum 不匹配立即上报）；④ 看构建（先宿主机 `mvn clean package -DskipTests`） |
| 禁止 | 不确认迁移就先删库；改 compose 端口映射后提交；跳过健康检查联调 |
| 为什么 | 多数「跑不通」是端口或未就绪；先排环境再怀疑代码 |

### Q5：Git 出现冲突怎么办

| 项 | 内容 |
| --- | --- |
| 场景 | 合并时 `ItemServiceImpl.java` 冲突 |
| 处理步骤 | ① 停手，不凭印象选边；② 同片冲突 → 两人一起以契约为准合并并补跑用例；③ 跨片冲突 → 说明有人越界，按规则 3 撤回并走「提需求 → 所有者改」；④ 合并后重跑构建与冒烟；⑤ 难以判定时宁可放弃本地改动重写，也不要两边都保留 |
| 禁止 | `push --force` 覆盖他人；冲突未解决就提交；「保留双方代码」糊过去 |
| 为什么 | 「两边都保留」编译期通过、运行期偶发，是最难排查的缺陷 |
