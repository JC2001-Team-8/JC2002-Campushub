## 1. 术语表

### 1.1 业务核心术语

| 术语 | 英文/编码 | 定义 | 易混淆点 |
| --- | --- | --- | --- |
| 商品 | Item | 用户发布的一件闲置物品记录，含标题、分类、成色、估价、交易区域、图片 1–9 张 | 与「订单明细」「交换包物品」区分：商品是主体，后两者是引用 |
| 分类 | Category | 预设字典（教材书籍、电子数码、生活用品、服饰、运动器材、其他等） | 用户**不可**自定义分类（Q-21 待确认） |
| 成色 | Condition | 预设枚举：全新、几乎全新、轻微使用痕迹、明显使用痕迹、有瑕疵 | 非自由文本 |
| 估价 | Estimated Price | **卖家自填**的参考金额，≥0，两位小数；**平台不定价、不校验合理性**，仅用于展示与交换包合计 | 极易被误解为平台定价 —— 所有展示位必须标注「用户自填，仅供参考」（R-13） |
| 交易区域 | TradeZone | 后台预设的地理单位（某校区 / 某周边社区），是权限校验、过滤、交付的最小地理范围 | 用户只能**勾选**，不能新增；一个用户可勾选 1–5 个 |
| 常用交易区域 | UserTradeZone | 用户勾选的 1–5 个交易区域，决定其可发布/可交易的范围 | 与「商品所属区域」区分 |
| 公共取货点 | PickupPoint | 归属于某交易区域的线下当面交付地点（图书馆门口、食堂门口、教学楼大厅、宿舍区门口、校门口、社区广场） | 非用户地址；一个取货点只属于一个区域 |
| 交换状态 | Swap Status | 商品是否接受交换的标记，展示为：可交换 / 暂不交换 / 交换中 / 已交换 | 「交换中」是**占用态**，不是设置项 |
| 交换包 | SwapBundle | 用户将自己的 **1–5 件**商品打包成的整体，用于发起交换；是交换的最小提议单位 | 不是购物车；包内商品必须同属一人 |
| 交换包估价合计 | Bundle Estimated Total | 包内商品估价之和，**仅展示**，不用于等价判定、不用于差价计算 | 与 OOS-03（不做现金补差价）直接相关 |
| 交换提议 | SwapProposal | 一方用自己的交换包，向另一方的 1 件或多件商品发起的交换请求 | 参与方**恰好两个**（proposer / target），无多人链（OOS-02） |
| 发起方 | Proposer | 交换提议的提出者，贡献自己的交换包 | — |
| 目标方 | Target | 交换提议的接收者，其商品被请求 | — |
| 反提案 | Counter Proposal | 目标方不接受原提议时，用自己的交换包提出的**反向新提议**；**仅允许一轮**（A-10） | 不是「还价」；不做现金补差 |
| 整包接受 | All-or-Nothing Accept | 目标方一次性接受提议中**全部**目标商品，同时占用交换包内**全部**商品 | **不支持部分接受**（OOS-04） |
| 整笔作废 | Whole-Deal Void | 交换涉及商品中**任意一件**被其他占用/下架/违规处置时，**整笔**交换作废并释放全部占用 | 与「整包接受」粒度对称（R-22 / R-24） |
| 占用 | Occupation | 商品被某笔进行中交易（订单或交换）独占的状态，体现为 `RESERVED`（订单占用）或 `SWAPPING`（交换占用） | **一物同时只能有一个占用**（R-23） |
| 库存预留 | Stock Reservation | 提交订单时立即占用商品并开始付款倒计时的机制，对应文案「已为你保留，剩余 mm:ss 付款」 | 占用发生在**下单时**，不是付款时（R-16） |
| 付款倒计时 | Payment Countdown | 订单创建后 **30 分钟**（A-01）内须完成付款，否则系统超时取消并释放商品 | 以**服务端时间**为准（R-19） |
| 模拟付款 | Mock Payment | 将订单直接标记为已付款的伪支付动作，**不接入任何真实支付通道**（OOS-01） | 页面必须标注「未产生真实扣款」 |
| 交换码 | SwapCode | 交换提议被整包接受后生成的**一次性**凭证，双方线下见面时核销，核销后进入双方确认阶段 | 仅提议双方可见；**只能核销一次**（R-26） |
| 双方确认 | Bilateral Confirmation | 交换码核销后，双方各确认一次（已交付 / 已收到），两次齐备才判定交换完成 | 同一方重复确认幂等（R-27） |
| 举报 | Report | 登录用户对商品提交的违规反馈，进入管理员处理队列 | 同一用户对同一商品重复举报幂等（R-17） |
| 违规下架 | Banned / Takedown | 管理员下架商品后的状态 `BANNED`；卖家**不可**自行重新上架 | 与卖家主动下架 `OFF_SHELF` 区分 |
| 处罚 | Penalty | 对用户的处置记录，类型含 `BAN_3D`（封禁三天）与 `ITEM_TAKEDOWN`（违规下架处置）；**永不删除**（R-32） | 处罚记录 ≠ 当前状态 |
| 封禁 | Ban | 默认且固定 **3 天（72 小时）**（A-03）的账号限制；到期**自动解封**（R-31） | 处罚期间用户仍可登录与申诉 |
| 自动解封 | Auto Unban | 定时任务将到期处罚置为 `EXPIRED` 并恢复用户普通角色 | 与管理员手动解封区分来源 |
| 申诉 | Appeal | 被处罚用户在处罚生效期内提交的异议请求；**提交后处罚仍生效**（不停表） | 申诉通过即立即解封（R-32） |
| 被处罚用户 | ROLE_RESTRICTED | 处于生效中处罚的用户，交易类写操作被禁止，但可登录、浏览、申诉 | 不是永久角色，解封后回到普通用户 |

### 1.2 状态与枚举术语

| 术语 | 取值 | 说明 |
| --- | --- | --- |
| 商品状态 | 草稿 / 在售 / 已预订 / 交换中 / 已售出 / 已下架 / 违规下架 | 「已预订」「交换中」为占用态，互斥 |
| 订单状态 | 待付款 / 已付款（待取货）/ 已交付待确认 / 已完成 / 已取消 / 超时取消 | 无「退款中」（本迭代不做退款） |
| 交换提议状态 | 待处理 / 已接受 / 已拒绝 / 已反提案 / 已过期 / 已取消 / 已完成 | 「已反提案」为中间态 |
| 交换包状态 | 草稿 / 已打包 / 交换中 / 已占用 / 已释放 / 已完成 | 「交换中」与「已占用」区分见状态机 §5.1 |
| 处罚状态 | 生效中 / 申诉中 / 已解封 / 已过期 | 申诉中处罚**仍生效** |
| 申诉状态 | 已提交 / 申诉通过 / 申诉驳回 | — |
| 评价状态 | 可评价 / 买家已评 / 卖家已评 / 双方已评 / 窗口关闭 | 不做差评，超期仅关闭 |

### 1.3 权限与工程术语

| 术语 | 定义 |
| --- | --- |
| 访客 | 未登录用户，仅只读浏览 |
| 注册用户 | 已登录的普通用户，是所有个人能力的基础角色 |
| 卖家 / 买家 | **关系角色**，不是注册身份：用户在自有商品上是卖家，在某笔订单/某次交换上是买家 |
| 管理员 | 单一治理角色 `ROLE_ADMIN`，**不参与交易**（P-00-A） |
| 系统定时任务 | `ROLE_SYSTEM`，执行超时取消、过期释放、自动解封等，无人工入口 |
| 本人原则 | 涉及自有资源的操作必须校验归属，失败返回 **403** 而非 404（P-00-B） |
| 幂等键 | 客户端生成的唯一键（假设 UUID v4，A-15），用于保证重复提交不产生重复副作用 |
| IDEM-A | 强幂等：重复请求返回与首次相同的结果 |
| IDEM-B | 幂等拒绝：重复请求明确失败，无副作用 |
| IDEM-C | 终态保护：已处终态时任何写操作失败，状态不变 |
| 条件更新 | 并发控制手段：`UPDATE ... WHERE id=? AND status=?`，受影响行数为 0 视为冲突 |
| 乐观锁 | 基于版本号的并发控制，与条件更新等价作用 |
| 工程骨架 | 迭代一交付的**可启动**前后端项目结构（Vue3+TS / Java 11 + Spring Boot 2.7.18 / PostgreSQL 15），**不含业务逻辑实现** |
| 接口清单 | 迭代一冻结的接口资源/方法/路径/权限/幂等/错误场景清单，**10/9 后不许新增** |
| 冻结候选 | 文档状态：内容已完备，等待用户确认待确认问题后即可冻结为基线 |
