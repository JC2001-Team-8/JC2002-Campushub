## 2. Challenges Faced and Solutions（挑战与解决）

本期最大的挑战都集中在**「如何在人力有限的前提下，把 83 个接口、25 张表、34 条规则的一致性长期锁住」**。
以下 5 个是真实发生且已解决的问题。

### 挑战 1：接口契约冻结后如何避免范围蔓延

**问题**：需求评审期间接口数量一度持续增长（从 60 余个涨到 83 个）。若冻结后仍可随意加接口，
前端会按不同版本的契约并行开发，联调阶段必然出现「我这边没有这个接口」的返工。
但完全不让改又会把真实缺陷锁死在契约里。

**解决方案**：建立**分级变更流程**，并写进 `api-freeze.md`。

| 措施 | 内容 |
| --- | --- |
| 硬时间点 | **2026-10-09 后不允许新增接口** |
| 允许的变更 | 修正文案、补充 `example`、补充**可选**响应字段（向后兼容）、修正错误 |
| 禁止的变更 | 增删接口、改路径/方法/operationId、删改 DTO 字段、收窄枚举、变更必填性、变更错误码语义 |
| 审批要求 | 影响面评估 + **3 人审批**（后端 / 前端 / 测试各一）+ 变更台账登记 |
| 唯一例外 | 占位数据（校区/区域/取货点）的**具体值**替换不算契约变更 |

**效果**：契约冻结后至今 **0 次未授权变更**；`/v3/api-docs` 与契约保持 **83/83 完全 1:1**。

### 挑战 2：Docker 构建慢与依赖缓存问题

**问题**：首次容器化构建耗时 **约 38 分钟**。根因有两个：
① 容器内全新构建需重新下载全部 Maven 依赖；
② 构建上下文包含 155 MB 的 `.mvnrepo/` 缓存目录，每次都要打包传输。
团队反馈「改一行代码要等半个多小时才能验证」，严重影响迭代速度。

**解决方案**：改变构建策略，让容器只负责**运行**，不负责**构建**。

| 措施 | 内容 |
| --- | --- |
| 默认 `Dockerfile` 改为运行镜像 | 只 `COPY target/campus-trade.jar`，不在容器内跑 Maven |
| 保留 `Dockerfile.build` | 供 CI 使用的容器内完整构建（含 `dependency:go-offline` 依赖层缓存） |
| 新增 `.dockerignore` | 排除 `.mvnrepo/`、`.git/`、日志、`data/` 等（构建上下文 155 MB → 49.6 MB）；**刻意不排除 `target/`**，因为运行镜像需要它 |
| 宿主机（或一次性容器）先打包 | 用 `maven:3.9-eclipse-temurin-11` + 本地 `.mvnrepo` 卷构建 |

**效果**：**38 分钟 → 9~10 秒**（约 **250 倍**提速）。修复过程中还解决了两个真实故障：
`base name (${RUNNER_IMAGE}) should not be blank`（Compose 传入空 build arg 覆盖默认值 → 改为硬编码 `FROM`）、
`COPY failed: stat target/campus-trade.jar`（`.dockerignore` 误排除 `target/`）。

### 挑战 3：并发占用与整笔作废的数据库级保证

**问题**：这是本项目最核心的业务难点——**「同一件商品同一时间只能被一个进行中交易占用」**，
而且订单占用（`RESERVED`）与交换占用（`SWAPPING`）必须**互斥**。
最初的设想是「下单前查一下商品状态，如果是在售就占用」，但这是典型的**「先查后改」竞态**：
两个买家同时查到「在售」，然后都会去占用，最后一个覆盖另一个 —— 商品被卖两次。

第二个难点是**交换的粒度**：交换包可含 1–5 件商品，
「其中一件被别人买走了」时该怎么办？部分占用会导致双方账目无法对齐。

**解决方案**：引入**占用台账 + 数据库级排他约束**，并把「整笔作废」作为交换粒度。

| 措施 | 内容 |
| --- | --- |
| 新增 `item_occupations` 台账 | 全库唯一表达「商品被谁占用」的真值来源；`released_at IS NULL` 表示进行中 |
| `items.status` 降级为**投影** | 仅用于快速查询，不作为判定依据（DD-01） |
| **部分唯一索引**兜底 | `uq_item_occ_active_item ON item_occupations(item_id) WHERE released_at IS NULL` —— **同一商品同时最多一条未释放占用**，由数据库强制 |
| 订单与交换天然互斥 | 因为共用同一个索引，不需要额外的互斥逻辑（R-23） |
| 条件更新判定胜负 | `UPDATE ... WHERE id=? AND status='IN_SALE'`，以 `affected rows` 判定；0 行即 409 冲突（R-18） |
| 冲突映射 | 唯一索引冲突（SQLState `23505`）映射为**对应域的 409 错误码**，而非 500 |
| 整笔作废 | 交换涉及商品中**任意一件**被占用/下架 → **整笔**作废并释放全部占用（R-24）；与「整包接受」（R-22）粒度对称 |

**效果**：并发正确性**由数据库保证**，不依赖应用层约定；
已在数据库中实测「两人抢同一件商品」只能一人成功，另一人得到 `409 ITEM_ALREADY_RESERVED`（时序图 §5 有完整刻画）。

### 挑战 4：一次性的契约→骨架生成，如何保证 83 个接口不跑偏

**问题**：83 个 operationId、73 条路径、99 个 schema 如果**手写**，
几乎必然出现拼写、路径、类型或 operationId 的偏差，而验收恰恰要求**1:1**。
手工核对 83 条也极其耗时且不可靠。

**解决方案**：写一个**只读契约**的一次性生成器 `tools/generate_api_skeleton.py`，
从 `openapi.yaml` 生成全部 Controller / DTO / Service，并保留脚本以便契约变更时**可重复再生成**。

**效果与过程中修掉的真实缺陷**（这部分是本期技术含量最高的调试）：

| # | 缺陷 | 现象 | 修复 |
| --- | --- | --- | --- |
| 1 | 共享参数 `$ref` 未解析 | 幂等参数**全部丢失**（实测 0 必填 / 0 可选，应为 16/16） | 解析 `components.parameters` |
| 2 | HTTP 头名 `Idempotency-Key` 含 `-` 不能作 Java 标识符 | 生成非法 Java | 新增 `safe_ident()`，并保住 `itemId` 不被小写化 |
| 3 | description 未转义换行/引号/反斜杠 | 大量 `unclosed string literal` 编译失败 | 加固 `esc()`（先转义反斜杠，再引号，再换行） |
| 4 | **生成器无条件删除手工 Controller** | `HealthController`/`FrozenSpecController` 被删，`/api/v1/health` 与 `/openapi/openapi.yaml` 变 404 | 加入 KEEP 保留清单 |
| 5 | **Controller 缺类级基础路径** | 接口注册到 `/items` 而非 `/api/v1/items`，**全部 404** | 加 `@RequestMapping("/api/v1")` |
| 6 | `PageResult<T>` 泛型退化为 `Object` | 16 个分页接口类型信息丢失 | 从 `allOf` 的 `content.items.$ref` 反推元素类型 |

> **关键教训**：缺陷 4、5、6 **只有真正启动并调用接口才会暴露**。
> 如果只做「编译通过」就交付，会把 83 个 404 的接口交给前端。

### 挑战 5：跨文档一致性如何不做成「人工核对地狱」

**问题**：到第 6 步时已有 24 份文档、25 张表、26 个枚举、93 个错误码、83 个 operationId、54 条 FR、70 个状态转换编号。
这些标识符在文档间被反复引用，人工核对必然遗漏。
实际上本期就**真的漏了一个**：`state-machines.md` 里 S-07（整笔作废）的规则引用写成了 **R-22**，
而 R-22 实际是「整包接受」，R-24 才是「整笔作废」。

**解决方案**：把一致性检查**脚本化 + 制度化**。

| 措施 | 内容 |
| --- | --- |
| 建立唯一真源 | 表名以 `V1__init_schema.sql` 为准；枚举以 `pg_enum` 为准；operationId 以 `openapi.yaml` 为准；FR 以 `requirements.md` 为准 |
| 脚本化交叉核对 | 自动提取文档中出现的表名/错误码/operationId/FR/规则/转换编号，逐一比对真源，**报告非法项** |
| 实测驱动 | 关键结论用**实库查询**验证（如 `pg_indexes` 数部分唯一索引），而非采信文档自述 |
| 缺陷登记制 | 发现的矛盾一律登记为 DDP/DQ 编号，**不擅自修改上游文档**，等授权后再改 |
| 交叉引用检查纳入验收 | 第 6 步把 13 项交叉引用检查写进验证记录，作为交付门槛 |

**效果**：
- 第 6 步 **13 项交叉引用检查全部通过**；过程中还纠正了 6 个真实问题（含 7 个**编造的错误码**、
  部分唯一索引**成员列举错误**、一处失效链接、Java 常量名与线上错误码混淆等）。
- 挑战 5 中发现的 **DDP-01 已在本步骤修复并闭环**（经用户授权，仅改 1 处引用，不动规则语义）。
