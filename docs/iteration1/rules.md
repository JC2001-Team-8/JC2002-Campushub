## 2. 账户与资料规则

### R-01 登录令牌有效期

| 项 | 内容 |
| --- | --- |
| 规则 | 登录成功后签发访问令牌，有效期 **7 天（假设 A-06）**。令牌过期或无效时，受保护接口统一返回未认证错误（401）。 |
| 前置条件 | 账号密码正确；账号存在 |
| 失败场景 | 账号不存在 / 密码错误 → 统一错误（**不区分**提示，避免账号枚举）；令牌过期 → 401 |
| 幂等 | 登录本身非幂等（每次产生新令牌），但**不影响业务状态** |
| 待确认 | Q-07：是否需要刷新令牌（refresh token）机制 |

### R-02 昵称规则

| 项 | 内容 |
| --- | --- |
| 规则 | 昵称非空，长度 **1–20 字符**（假设 A-09），**不要求唯一**（假设 A-04） |
| 失败场景 | 空 / 超长 / 含违规词（迭代一无敏感词库，故仅长度校验，Q-21） |
| 幂等 | 更新操作天然幂等（相同值重复写入结果一致） |

### R-03 图片格式与大小

| 项 | 内容 |
| --- | --- |
| 规则 | 允许格式：JPG、PNG、WebP；单张 ≤ **5MB**（假设 A-05）；头像 1 张，商品图 1–9 张 || 失败场景 | 格式不符 → 明确错误；超过大小 → 明确错误；上传空文件 → 拒绝 |
| 幂等 | 上传接口按文件内容哈希去重可选；重复上传同一文件不应产生损坏数据 |

## 3. 商品规则

### R-10 商品发布必填项

| 项 | 内容 |
| --- | --- |
| 规则 | 必填：标题（1–60 字符）、分类、成色、估价、交易区域、至少 1 张图片；可选：描述（≤1000 字符） |
| 前置条件 | 卖家：已登录、未被处罚、**已勾选至少 1 个常用交易区域**；所选交易区域 ∈ 本人已勾选区域 |
| 失败场景 | 缺必填 → 逐字段错误；区域不在本人已勾选集合 → 拒绝；被处罚 → 拒绝并返回解封时间 |
| 副作用 | 商品状态 = IN_SALE；写创建审计 |
| 幂等 | **IDEM-A**：请求携带幂等键时，重复提交只创建一件商品 |

### R-11 商品编辑限制

| 项 | 内容 |
| --- | --- |
| 规则 | 仅本人可编辑。**占用态（RESERVED / SWAPPING）禁止修改**：标题、估价、分类、成色、交易区域；允许修改：描述、图片（追加/替换，仍需 ≥1 张）。`SOLD` 状态禁止任何编辑（终态）。 |
| 理由 | 已占用商品的关键字段被改动会破坏订单/交换快照的可信度 |
| 失败场景 | 非本人 → 403；占用态改关键字段 → 409；终态 → 409 |
| 幂等 | 相同内容重复编辑结果一致（幂等更新） |

### R-12 图片数量限制

| 项 | 内容 |
| --- | --- |
| 规则 | 商品 1–9 张；**首图为封面**；删除后仍须 ≥1 张；调整顺序即调整封面 |
| 失败场景 | 0 张 → 拒绝保存；>9 张 → 拒绝；删除最后一张 → 拒绝 |

### R-13 估价语义（重要，防误解）

| 项 | 内容 |
| --- | --- |
| 规则 | 「估价」是**卖家自填的参考金额**（≥0，两位小数），用于展示与交换包合计。**它不是平台定价，不是权威估值，不构成任何价格承诺**；平台不校验其合理性。 |
| 展示 | 商品详情、购物车、订单、交换包合计均标注「用户自填估价，仅供参考」 |
| 与交换的关系 | 交换包合计**仅展示**；平台**不做等价判定、不做差价计算**（OOS-03） |
| 快照要求 | 下单/发起交换时**必须快照**当时估价，商品后续编辑不影响已有订单/交换的展示值 |
| 待确认 | Q-22：估价上限是否需要限制（如 ≤100000）？ |

### R-15 交易区域归属与跨区禁止 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 1 | 用户只能从预设交易区域列表中勾选 **1–5 个**常用区域，不可自由输入，不可读定位（OOS-05） |
| 规则 2 | 商品所属交易区域必须 ∈ 卖家已勾选区域 |
| 规则 3 | 下单时：商品区域 = 订单区域；买家必须已勾选该区域 |
| 规则 4 | 发起交换时：交换包区域 = 目标商品区域 = 提议区域；双方均须已勾选该区域 |
| 规则 5 | 取货点所选区域必须 = 订单/提议区域 |
| 规则 6 | **任何跨区域组合一律拒绝**（OOS-07），返回明确错误 |
| 失败场景 | 区域不一致 → 明确错误「商品不在你的常用交易区域」/「不支持跨区交易」 |
| 幂等 | 校验类规则天然幂等 |

## 4. 购买与订单规则

### R-16 库存占用与释放 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 提交订单即**占用**商品：商品状态 → `RESERVED`，并建立占用关系（OrderItem ↔ Item）。**同一商品同一时间最多被一笔未终结订单占用**。 |
| 占用生效时点 | 提交订单成功的同一事务内（**不是付款时**），以确保「已为你保留 15:00」的承诺成立 |
| 释放时点 | ① 买家主动取消（待付款）② 超时取消 ③ 商品被管理员违规下架联动作废 ④ 订单完成（商品转 SOLD，占用自然终结） |
| 不释放的情况 | 已付款且待交付：**长期保持占用**，直到完成或管理员介入 |
| 失败场景 | 商品已被占用 → 拒绝下单，返回「商品已被占用」；并发下**只允许一个请求成功** |
| 幂等 | 释放操作**IDEM-B**：重复释放无副作用，商品状态不被二次改写 |
| 并发 | 必须用条件更新（`WHERE status='IN_SALE'`）或行级锁；禁止「先查后改」 |
| 与交换的关系 | 同一商品**不可能**同时被订单占用和被交换占用（R-23 互斥） |

### R-07 付款倒计时与超时释放 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 订单创建成功即记录 `expireAt = createdAt + 30 分钟`（假设 A-01）。前端倒计时**必须**由服务端返回的 `expireAt`/剩余秒数驱动，**禁止**前端自行推算（R-19）。 |
| 展示文案 | 「已为你保留，剩余 15:00 付款」——剩余时间随时间递减 |
| 超时触发 | 定时任务每分钟扫描 `status = PENDING_PAYMENT AND now > expireAt`：订单 → `TIMEOUT_CANCELLED`，商品 → 释放回 `IN_SALE` |
| 边界 | 恰好等于 `expireAt`：以「已超时」处理（`now >= expireAt` 即超时，避免歧义） |
| 已付款保护 | 已是 `PAID` 的订单**绝不**被超时任务取消（条件更新保证） |
| 幂等 | 超时任务 **IDEM-B**：同一订单只取消一次；重复执行不重复释放、不重复发通知 |
| 失败场景 | 超时后尝试付款 → 拒绝，返回「订单已超时取消」+ 当前状态 |
| 并发 | 付款 与 超时取消 并发时，**只有一个成功**（条件更新 `WHERE status='PENDING_PAYMENT'`） |

### R-04 购物车规则

| 项 | 内容 |
| --- | --- |
| 规则 | ① 不可将自己的商品加入购物车；② 同一商品不重复加入（已存在则保持原条目）；③ 商品被占用/售出/下架时，购物车条目标记为**不可结算**并提示原因；④ 购物车列表**按卖家分组**；⑤ 下单成功后移除已下单条目 |
| 失败场景 | 加自家商品 → 拒绝；商品已占用 → 拒绝加入或标记失效 |
| 幂等 | 加入购物车 **IDEM-A**（重复加入不产生重复条目） |
| 待确认 | Q-23：购物车是否支持数量（闲置交易多为单件，假设**数量固定为 1**） |

### R-05 订单卖家唯一性与拆单

| 项 | 内容 |
| --- | --- |
| 规则 | **一笔订单只包含一个卖家的商品**。若购物车选中项跨越多个卖家，提交时**自动拆成多笔订单**（每卖家一笔），每笔订单独立倒计时、独立付款、独立交付。 |
| 响应要求 | 提交订单接口必须返回**生成的订单列表**，并明确告知拆单结果 |
| 幂等 | 拆单结果必须稳定：同一幂等键重复提交返回**同一组订单**，不得重复拆单 |
| 失败场景 | 某卖家商品已被占用 → 该笔拆分失败；语义待确认 **Q-24**（假设：**整批失败**，不产生部分下单，避免用户困惑） |

### R-06 公共取货点选择

| 项 | 内容 |
| --- | --- |
| 规则 | ① 取货点必须属于订单交易区域；② 本迭代定为**付款后选择**（订单 `PAID` 状态下可改，`DELIVERED` 后不可改）；③ 未选择取货点前，卖家**不可**标记交付 |
| 失败场景 | 跨区域取货点 → 拒绝；未付款就选点 → 拒绝（或允许但以最终付款为准，Q-25：假设**拒绝**）；已交付后改点 → 拒绝 |
| 幂等 | 选择操作**IDEM-A**：重复选择同一点不产生重复记录 |
| 待确认 | Q-25：是否允许在提交订单时预选取货点？ |

### R-08 模拟付款

| 项 | 内容 |
| --- | --- |
| 规则 | `POST /orders/{id}/mock-pay` 仅将订单标记为 `PAID`，记录 `paidAt` 与 `payChannel = "MOCK"`。**不接入任何真实支付通道**（OOS-01），不产生资金流水、不支持退款。 |
| 前置条件 | 订单归属本人；状态为 `PENDING_PAYMENT`；`now < expireAt`；未被处罚 |
| 失败场景 | 已付款 → **IDEM-A** 返回首次成功结果（前端可安全重试）；已超时/已取消 → 明确失败；非本人 → 403 |
| 幂等 | **IDEM-A**：重复付款请求返回与首次一致的「已付款」结果，**不得**重复记录付款时间或改变状态 |
| 待确认 | Q-26：模拟付款是否需要人工输入（如固定验证码）以模拟真实交互？假设**不需要**，一键成功 |

### R-09 订单终态保护

| 项 | 内容 |
| --- | --- |
| 规则 | `COMPLETED`、`CANCELLED`、`TIMEOUT_CANCELLED` 为终态，**不可回退、不可重复推进**。对终态订单的任何写操作返回 409 + 当前状态。 |
| 幂等 | **IDEM-C**（终态保护） |
| 例外 | 管理员治理场景可**读取**终态订单用于举证，但**不得**修改其状态 |

### R-14 评价前置与互评窗口

| 项 | 内容 |
| --- | --- |
| 规则 | ① 仅订单 `COMPLETED` 后可评价；② 买卖双方**各评一次**，互不影响（不要求同时）；③ 评价窗口 **7 天**（假设 A-07），超期关闭且**不自动生成差评**；④ 迭代一评价**不参与排序**（OOS-09） |
| 失败场景 | 未完成订单评价 → 拒绝；同一方重复评价 → 拒绝；窗口关闭后评价 → 拒绝 |
| 幂等 | **IDEM-B**：同一订单同一方第二次评价明确失败 |
| 待确认 | Q-20：评价是否公开？是否允许修改/删除？假设：公开可见，**不可修改**，暂不支持删除 |

## 5. 全局一致性与幂等规则

### R-17 重复提交与幂等键 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 所有**写操作中会产生不可逆业务后果**或**占用资源**的接口，必须支持幂等键（`Idempotency-Key` 请求头或请求体字段）： |
| 必须支持的接口 | 提交订单、模拟付款、发起交换提议、接受提议、拒绝提议、反提案、确认收货、确认交换、校验交换码、封禁、解封、提交申诉、发布商品 |
| 语义 | ① 同一幂等键 + 同一接口 + 同一用户 → 返回**首次结果**（IDEM-A）；② 幂等键过期时间建议 **24 小时**（假设 A-08）；③ 幂等键缺失时，服务端按「无幂等保护」处理但**业务层仍须做状态校验**（如占用检查），保证不会产生两次占用 |
| 两层防护 | **幂等键（防重复提交）+ 条件更新（防并发竞争）**，两者缺一不可 |
| 失败场景 | 幂等键复用但请求体不同 → 返回冲突错误（防「同键异义」） |
| 待确认 | Q-27：幂等键由前端生成（UUID）还是服务端返回？假设**前端生成 UUID v4** |

### R-18 并发控制与乐观锁 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 所有状态转换使用 **条件更新**（`UPDATE ... WHERE id = ? AND status = ?`）或**版本号乐观锁**（`WHERE version = ?`）。受影响行数为 0 即视为并发冲突，返回 409 + 当前状态。 |
| 禁止 | 禁止「先查询、再判断、后无条件更新」的两段式写法（存在竞态窗口） |
| 关键竞争点 | ① 两个买家下单同一商品；② 同一订单「付款 vs 超时取消」；③ 两个用户对同一商品发起交换；④ 同一交换提议「接受 vs 拒绝 vs 过期」；⑤ 处罚「到期自动解封 vs 管理员手动解封」；⑥ 治理下架 vs 卖家编辑 |
| 一致性 | 同一聚合内的状态 + 副作用必须同事务；跨聚合（如订单取消 + 商品释放 + 通知）允许最终一致，但必须有幂等补偿与对账手段 |
| 失败场景 | 冲突 → 409，响应体携带最新可用状态，前端据此刷新 |
| 验证要求 | 接口测试必须包含并发用例（≥2 并发）验证「只有一个成功」 |

### R-19 时间语义

| 项 | 内容 |
| --- | --- |
| 规则 | ① 所有业务时间以**服务端时间为准**；② 倒计时/过期判断**不得**信任前端传入的剩余时间；③ 时间存储统一使用带时区的时间类型，业务时区假设为 **Asia/Shanghai**（Q-28）；④ 接口返回 `expireAt`（绝对时间）与 `remainingSeconds`（便于前端直接展示） |
| 幂等 | 时间判断本身幂等；定时任务的判断条件必须可在重复执行下保持稳定 |
| 失败场景 | 前端传入伪造时间 → 服务端忽略 |

## 6. 交换规则

### R-20 交换状态设置

| 项 | 内容 |
| --- | --- |
| 规则 | 卖家可对每个商品设置「接受交换 / 不接受交换」，并在详情页展示交换状态（可交换 / 暂不交换 / 交换中 / 已交换） |
| 限制 | 商品处于占用态或终态时，**不可**改为「接受交换」 |
| 幂等 | 设置操作幂等（重复设置同一值结果一致） |

### R-21 交换包件数与归属

| 项 | 内容 |
| --- | --- |
| 规则 | ① 交换包包含 **1–5 件**商品，超出范围直接拒绝；② 包内所有商品**必须属于同一 owner**；③ 同一商品**同一时间只能存在于一个进行中的交换包**；④ 包被进行中提议引用期间**不可修改组成** |
| 失败场景 | 0 件或 >5 件 → 拒绝；包含他人商品 → 拒绝；商品已在其他进行中包 → 拒绝；修改进行中包 → 拒绝 |
| 幂等 | 增删物品幂等（重复添加同一物品不产生重复项） |

### R-22 整包接受、不可部分接受 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 交换提议的接受是**整包 all-or-nothing**：接受即接受提议中列出的**全部**目标商品，并占用交换包内**全部**商品。**不支持**只接受部分物品、不支持逐件接受/拒绝（OOS-04）。 |
| 接口语义要求 | 接受接口**不得**提供 item 级选择参数；如请求体中出现物品子集，应拒绝或忽略（契约中明确：接受接口无物品列表参数） |
| 只想要部分怎么办 | ① 拒绝原提议；② 发起**反提案**，在反提案中给出自己想要的组合（R-28） |
| 失败场景 | 任何一件目标商品已被占用 → 整个接受失败（R-23、R-24），不产生部分占用 |
| 幂等 | 接受 **IDEM-B**：重复接受失败，返回 409 + 「已接受」状态；**不得**重复生成交换码 |

### R-23 同时占用互斥 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | **同一商品同一时间只能被一个进行中的占用持有**，占用来源有两种：① 订单占用（`RESERVED`）② 交换占用（`SWAPPING`）。两种占用**互斥**，且各自内部也互斥。 |
| 占用标识 | 建议记录 `occupiedByType`（ORDER / SWAP）与 `occupiedByRefId`，便于排查 |
| 失败场景 | 已被占用 → 后到请求明确失败，返回「商品已被占用」；并发下**只有一个成功** |
| 幂等 | 同一占用方重复发起不重复占用（IDEM-A）；释放幂等（IDEM-B） |
| 验证要求 | 必须提供并发用例：两笔交换同时请求同一商品，断言恰有一个成功 |

### R-24 整笔作废 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 交换涉及的**任一商品**出现以下情况时，**整笔交换作废**（不是部分作废）：<br>① 被其他订单占用；② 被其他交换占用；③ 被卖家主动下架；④ 被管理员违规下架/处置；⑤ 商品被删除（若允许）。 |
| 后果 | 提议 → `CANCELLED`（原因=整笔作废）；**全部**占用一次性释放；所有涉及商品回到 `IN_SALE`（被下架的除外，保持 `OFF_SHELF`/`BANNED`）；通知双方并说明作废原因 |
| 为什么整笔 | 交换是「包对包」的价值对等行为，缺一件即不成立；部分执行会留下不公平的半成品交易 |
| 幂等 | **IDEM-B**：只作废一次；重复触发无副作用、不重复通知 |
| 与 R-22 的关系 | 因为不接受部分，所以失败也必须是整笔失败——接受与作废在粒度上对称 |

### R-25 72 小时过期释放

| 项 | 内容 |
| --- | --- |
| 规则 | 交换提议有效期 **72 小时**（假设 A-02）：`expireAt = createdAt + 72h`。到期由定时任务将 `PENDING` 提议置为 `EXPIRED`，并释放**全部**占用。 |
| 边界 | `now >= expireAt` 即过期；**已 `ACCEPTED` 的提议不参与过期**（避免已进入交付环节的交换被系统打断） |
| 幂等 | **IDEM-B**：同一提议只过期一次；占用只释放一次；通知只发一次 |
| 失败场景 | 过期后尝试接受/拒绝 → 拒绝，返回「提议已过期」 |
| 并发 | 「接受 vs 过期」并发时只能一个成功（条件更新） |
| 待确认 | Q-29：72 小时是否从发起时刻算，还是从对方首次查看算？假设**从发起时刻算** |

### R-26 交换码一次性 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | ① 提议被**整包接受**后生成交换码；② 交换码在**同一提议内唯一**，双方可见；③ 交换码**只能成功核销一次**（一次性凭证），核销后立即失效；④ 核销是「双方线下见面凭码确认」的凭证，核销后进入双方确认阶段 |
| 生成要求 | 建议足够随机（防猜解）且便于口述（如 6–8 位，含字母数字）——具体规则待确认 Q-30 |
| 失败场景 | 重复核销 → 失败「交换码已失效」；错误码 → 失败；提议非 ACCEPTED 状态 → 失败 |
| 幂等 | **IDEM-B**：第二次核销明确失败，不产生副作用 |
| 安全 | 交换码**不得**出现在公开列表接口中，仅提议双方可读取 |

### R-27 双方确认

| 项 | 内容 |
| --- | --- |
| 规则 | 交换码核销后，**双方各确认一次**（交付方确认「已交付」、接收方确认「已收到」）。**两次确认齐备**才判定交换完成：全部商品 → `SOLD`，提议 → `COMPLETED`。 |
| 前置 | 提议 `ACCEPTED`；交换码已核销；该方此前未确认 |
| 失败场景 | 未核销就确认 → 拒绝；同一方重复确认 → **IDEM-A** 返回成功态且不重复计数 |
| 幂等 | 单方确认 IDEM-A；「双方齐备 → 完成」的清结算 IDEM-A（重复触发不重复置 SOLD） |
| 待确认 | Q-15：一方长期不确认如何处理（假设：本迭代**不做**自动完成/自动取消，由管理员介入） |

### R-28 反提案仅一轮

| 项 | 内容 |
| --- | --- |
| 规则 | 目标方收到 `PENDING` 提议后，可**反提案一次**：原提议 → `COUNTERED`（释放占用），生成一条新提议（proposer=原目标方，target=原发起方，状态 `PENDING`，同样 72 小时）。新提议只能被**接受或拒绝**，**不得再次反提案**（即最多「一轮反提案」）。 |
| 理由 | 迭代一不做站内聊天（OOS-08），无限反提案等同于用状态机模拟聊天，会产生冗长拉锯与占用长期冻结 |
| 失败场景 | 对 `COUNTERED` 的提议再次反提案 → 拒绝；对反提案再反提案 → 拒绝 |
| 幂等 | **IDEM-B**：同一提议只允许一次反提案 |
| 待确认 | Q-31：是否允许「反提案的反提案」？假设**不允许** |

## 7. 管理员治理规则

### R-30 封禁默认三天

| 项 | 内容 |
| --- | --- |
| 规则 | 管理员封禁用户时，**默认且固定 3 天（72 小时）**（假设 A-03）：`endAt = now + 72h`。不提供时长选择参数（Q-09：假设**固定不可调**）。 |
| 前置条件 | 必须填 `reason`；目标用户当前**无**生效中处罚（Q-10：假设**拒绝重复封禁**）；目标**不是**管理员 |
| 副作用 | 用户 → `ROLE_RESTRICTED`；创建处罚记录（ACTIVE）；站内通知；写审计 |
| 失败场景 | 无 reason → 拒绝；已在处罚中 → 拒绝；目标为管理员 → 拒绝 |
| 幂等 | **IDEM-A**：同一幂等键重复封禁不产生第二条生效处罚 |
| 与处罚记录的关系 | 封禁必然产生一条处罚记录，记录不可删除（R-32） |

### R-31 自动解封

| 项 | 内容 |
| --- | --- |
| 规则 | 定时任务每分钟扫描 `status IN (ACTIVE, APPEALING) AND now >= endAt` 的处罚：置为 `EXPIRED`，用户恢复 `ROLE_USER`，记录解封时间与来源=系统。 |
| 幂等 | **IDEM-B**：同一处罚只解封一次；重复执行不重复写记录、不重复发通知 |
| 并发 | 「到期自动解封」与「管理员手动解封/申诉通过」并发时，**只有一个成功**（条件更新 `WHERE status IN (ACTIVE, APPEALING)`） |
| 边界 | 申诉中的处罚（`APPEALING`）**照常到期**（处罚不停表），到期后申诉自动结案（Q-18） |

### R-32 处罚记录保留与申诉

| 项 | 内容 |
| --- | --- |
| 规则 | ① 处罚记录**永不删除**，无论到期、解封或申诉结果；② 记录包含：对象用户、类型、原因、起止时间、操作管理员、申诉结论；③ 用户可在处罚生效期内提交**申诉**（`SUBMITTED`）；④ 管理员处理申诉必须填写处理意见；⑤ 申诉通过 → 立即解封（LIFTED，结论=申诉通过）；申诉驳回 → 处罚继续生效至 `endAt` |
| 失败场景 | 对已解封处罚申诉 → 拒绝（Q-17）；重复申诉同一处罚 → 拒绝或返回已有申诉；无处理意见 → 拒绝 |
| 幂等 | 提交申诉 IDEM-A；处理申诉 IDEM-A（重复处理返回首次结论） |
| 可见性 | 全量处罚记录仅管理员可见；用户仅可见自己的记录（矩阵 2.11） |

### R-33 处罚期间交易写入禁止

| 项 | 内容 |
| --- | --- |
| 规则 | 处罚生效期内（`ACTIVE` / `APPEALING`），用户被禁止：发布/编辑商品、加购物车、下单、付款、创建交换包、发起/接受/拒绝/反提案交换、评价、修改昵称头像。**允许**：登录、浏览、查看自己的处罚与订单、提交申诉、勾选交易区域、举报、下架自己的商品（白名单详见 `permission-matrix.md` §8） |
| 失败场景 | 被处罚用户执行禁写操作 → 明确错误 + **返回解封时间**（便于前端提示） |
| 幂等 | 校验类规则幂等 |
| 特殊边界 | 处罚前**已存在**的进行中订单/交换的收尾操作（卖家交付、买家确认收货）是否允许：**待确认 Q-13**（假设**允许收尾**，否则交易永久卡死） |

### R-34 治理动作审计

| 项 | 内容 |
| --- | --- |
| 规则 | 所有治理动作（下架、恢复、封禁、解封、申诉处理、举报处理）**必须**记录：操作者 ID、操作时间、对象类型与 ID、原因/意见（必填）、动作前后状态。 |
| 契约要求 | 治理类接口的 `reason` 字段为**必填**；缺失直接拒绝 |
| 幂等 | 审计记录为**追加写**，重复执行必须被幂等键或状态校验拦截，避免产生重复审计噪音 |
| 可见性 | 审计日志仅管理员可读 |
| 待确认 | Q-32：审计日志是否需要提供导出？假设**不需要** |

### R-35 违规商品下架联动 【最高优先级】

| 项 | 内容 |
| --- | --- |
| 规则 | 管理员下架商品（`BANNED`）时，若该商品存在**进行中占用**，必须**联动处理**：<br>① 若被订单占用（`RESERVED`）→ 订单取消（来源=系统治理），释放商品；<br>② 若被交换占用（`SWAPPING`）→ **整笔交换作废**（R-24），释放全部相关商品。 |
| 理由 | 违规商品不得继续参与交易，但也不能让买家/交换对方凭空卡在中间状态 |
| 通知 | 必须通知所有受影响方（买家、交换双方、卖家）并说明原因 |
| 幂等 | 下架动作 **IDEM-A**（重复下架不产生重复记录）；联动作废 **IDEM-B**（只作废一次） |
| 失败场景 | 无 reason → 拒绝下架 |

## 8. 规则间的依赖与冲突检查

| 检查项 | 结论 |
| --- | --- |
| R-22（整包接受）与 R-24（整笔作废）粒度是否一致？ | **一致**：要么全成，要么全废，不存在部分占用 |
| R-16（订单占用）与 R-23（交换占用）是否互斥？ | **是**：同一商品不能同时 `RESERVED` 与 `SWAPPING`，由 R-18 条件更新保证 |
| R-07（超时释放）与 R-08（模拟付款）是否竞争？ | **是**：并发时只允许一方成功（条件更新 `WHERE status='PENDING_PAYMENT'`） |
| R-31（自动解封）与申诉通过是否竞争？ | **是**：条件更新保证只解封一次 |
| R-15（同区域）与 R-06（取货点）是否一致？ | **是**：取货点必须 ∈ 订单区域，且订单区域 = 商品区域 |
| R-17（幂等）覆盖了所有资源占用类接口？ | 覆盖：下单、付款、发起交换、接受、确认收货、确认交换、封禁、解封、申诉 |
