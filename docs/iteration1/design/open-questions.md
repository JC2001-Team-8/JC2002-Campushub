## 1. 编号规则与处理原则

| 项 | 说明 |
| --- | --- |
| 编号 | `DQ-xx`（Database Question），与迭代一需求文档的 `Q-xx` 独立，避免混淆 |
| 原则 1 | **不扩大范围**：本文档只登记「建模时必须做出选择」的点，不新增业务功能 |
| 原则 2 | **已给出可执行默认值**：每个问题都已有落地实现（否则无法完成迁移验证），确认后可低成本调整 |

| 优先级 | **P0** = 阻塞接口契约冻结；**P1** = 阻塞后端实现；**P2** = 可延后 |

## 3. 数据库设计新增问题（DQ 系列）

### 3.1 P0 —— 阻塞接口契约冻结

| 编号 | 问题 | 当前落地（已有默认值） | 若改变的影响 |
| --- | --- | --- | --- |
| **DQ-01** | **「草稿」商品状态是否启用？** 需求 A-14/Q-14 假设「发布即上架，不使用草稿」，但状态机 §2.1 定义了 `DRAFT`，V1 也已建入枚举 | 已建 `DRAFT`，但**默认不使用**（发布即 `IN_SALE`）；`ck_items_published_when_on_sale` 要求 `IN_SALE/RESERVED/SWAPPING` 必须有 `published_at`，`DRAFT` 可为空 | 若确认不用草稿：可保留枚举值（不影响），或新增迁移移除；接口契约需明确「发布接口无草稿态」 |
| **DQ-02** | **交易区域能否被停用（软下线）？** 表中有 `is_active`，但需求未定义停用语义 | 已建 `is_active BOOLEAN`，默认 `TRUE` | 若确认可停用：需明确「已勾选该区域的用户怎么办」「历史商品是否仍可见」，接口需相应过滤逻辑 |
| **DQ-03** | **一个用户勾选的 1–5 个常用区域之间是什么关系？** 需求仅要求「商品/订单/交换同区域」（R-15），未定义多区域用户的一次交易可否跨自己勾选的区域 | 仅存 `user_trade_zones` 多行，**不做区域互通**；每次交易强校验同一 `trade_zone_id` | 若允许「相邻区域互通」（OOS-07 迭代 N），需引入区域组表，属范围外 |
| **DQ-04** | **`pickup_points` 是否需要开放时间/可用时段？** 需求 Q-03 提到「开放时间」但未定义 | 当前只有 `description` 文字说明，**无时段字段** | 若需要：新增时段字段或关联表（属迭代二范围） |
| **DQ-05** | **处罚是否允许「时长可调 / 延长 / 覆盖」？** 假设固定 3 天且拒绝重复封禁（A-03 / Q-09 / Q-10）；`uq_penalties_one_active` 已强制「同时态最多一条生效 BAN_3D」 | 固定 72h；重复封禁**被数据库拒绝** | 若允许延长/覆盖：需先移除或放宽该部分唯一索引，属**结构性变更** |
| **DQ-06** | **审计日志是否需要保留策略与导出？** R-34 要求留痕，Q-32 假设不需导出 | `audit_logs` 只追加，无归档策略 | 若有合规保留期要求，需新增归档迁移与清理任务 |

### 3.2 P1 —— 阻塞后端实现

| 编号 | 问题 | 当前落地 | 说明 |
| --- | --- | --- | --- |
| **DQ-07** | **「商品占用态」与「占用台账」如何保持强一致？是否允许数据库触发器兜底？** | 设计为**应用层同事务维护**：写 `item_occupations` 的同时更新 `items.status`；`items.status` 是投影/缓存 | 用户明示「不实现业务逻辑」，故未建同步触发器；已提供对账查询 `verify_schema.sql` §11。若希望数据库兜底，可新增触发器迁移 |
| **DQ-08** | **交换码的碰撞与重试策略？** Q-30 未确认格式 | `code VARCHAR(16) UNIQUE`，种子用 7 位（`SWP8A2F`） | 需确认长度与字符集；接口层需实现「唯一冲突时重试生成」 |
| **DQ-09** | **幂等记录的清理策略与「同键异义」判定口径？** R-17/E-16 要求同键不同请求体需冲突 | `idempotency_records.request_hash` + `expires_at`（默认 24h，A-08）；`status IN_PROGRESS/COMPLETED/FAILED` | 需确认：`request_hash` 算法、并发同键时的等待/拒绝策略（`IN_PROGRESS` 的处理）、过期清理任务归属 |
| **DQ-10** | **`items.deleted_at` 软删除对治理可见性的影响？** | 软删除仅 `items` / `swap_bundles`；**处罚/申诉/订单/交换记录永不删除**（R-32） | 需确认：软删除商品在管理员后台是否仍可见（应可见，用于举证） |
| **DQ-11** | **通知是否需要去重 / 批量 / 保留期？** Q-05 待确认是否仅站内 | 每次事件一条 `notifications`；`ref_type`+`ref_id` 支持跳转 | 需确认：同一事件重复触发是否允许重复通知（R-07/R-25 要求「不重复发通知」） |
| **DQ-12** | **评价是否可修改 / 删除 / 公开？** Q-20 假设公开、不可修改、暂不支持删除 | `reviews` 有 `version`，无 `deleted_at`；唯一索引保证同一交易同一方一次 | 若允许修改：复用 `version` 条件更新即可；若允许删除：需新增软删除列（**结构性变更**） |
| **DQ-13** | **`swap_bundles` 释放后能否复用？** 状态机 §5 的 `RELEASED` 允许「包可再次使用或修改」 | 已允许：`swap_bundle_items.item_status` 区分 `ACTIVE/RELEASED/COMPLETED`，`uq_swap_bundle_items_active` 只约束 `ACTIVE` | 需确认复用时「历史提议保留原快照」的期望（当前 `swap_proposal_items` 有估价快照，但包内组成未做版本快照） |

### 3.2.1 P1 —— 接口契约阶段新增发现（DQ-26 / DQ-27）

> 由接口契约阶段（`openapi.yaml` + `idempotency-and-concurrency.md`）复核发现，已在本轮修正/登记。

| 编号 | 问题 | 当前落地 | 说明与建议 |
| --- | --- | --- | --- |
| **DQ-26** | **提议处于 `ACCEPTED` 阶段时，交换商品被违规下架**，`swap_codes` 是否应置为 `EXPIRED`？ | **已可表达但规则未声明**：`ck_swap_codes_verified_trace` 允许 `EXPIRED`（且 `verified_at IS NULL`）；但 `rules.md` R-35 / `state-machines.md` S-13 未明确说明该路径是否顺带把交换码置为 `EXPIRED` | 当前**安全**：契约中 `verifySwapCode` 要求提议状态为 `ACCEPTED`，提议被作废（`CANCELLED`）后无法核销。建议明确「作废时同时把未核销的交换码置 `EXPIRED`」以消除悬挂码。**不阻塞冻结** |
| **DQ-27** | **FR-604 评价窗口关闭的扫描条件是否排除终态 `BOTH_REVIEWED`？** | ✅ **本轮已修正**（原实现有缺陷）：V1 的部分索引条件为 `review_status <> 'WINDOW_CLOSED'`，会把终态 `BOTH_REVIEWED` 纳入扫描并**回退**为 `WINDOW_CLOSED`，违反评价状态机 R-05 的 **IDEM-C 终态保护**（`BOTH_REVIEWED` 与 `WINDOW_CLOSED` 同为终态） | 已修正为仅覆盖活跃态：`review_status IN ('OPEN','BUYER_REVIEWED','SELLER_REVIEWED')`。落地：① 新增迁移 **`V4__fix_review_window_index.sql`** 重建 `idx_orders_review_window`；② `openapi.yaml` 的 `runReviewWindowCloseTask` 扫描条件与 `x-locking` 同步修正；③ 迁移内含只读数据自检（检查是否存在「双方已评却被标记窗口关闭」的异常行） |

### 3.3 P2 —— 可延后（不阻塞冻结）

| 编号 | 问题 | 当前落地 | 说明 |
| --- | --- | --- | --- |
| **DQ-14** | **PostgreSQL ENUM 的演进成本**：新增状态值需要 `ALTER TYPE ... ADD VALUE`（PG12+ 可在事务外执行），删除/改名成本高 | 全部状态使用 ENUM（最贴合「枚举与状态机一致」的验收要求） | 若预期状态频繁变动，可评估改为「字典表 + 外键」。**当前不推荐改**（迭代一状态已冻结） |
| **DQ-15** | **是否需要数据库分区？** 日志类表（`audit_logs`、`notifications`、`idempotency_records`）会持续增长 | 使用普通表 + 时间索引 | 迭代一数据量极小，分区属**生产级优化**（OOS-17 明确不做） |
| **DQ-16** | **`condition_snapshot` / `title_snapshot` 是存文本还是存外键？** 快照需抗后续编辑 | 存**文本快照**（`order_items.condition_snapshot VARCHAR(32)`、`title_snapshot VARCHAR(60)`） | 若成色字典文案改名，历史订单保留旧文案——需确认这是期望行为 |
| **DQ-17** | **`order_no` / `proposal_no` 的生成规则与长度？** | `VARCHAR(32) UNIQUE`，种子为 `ORD-DEMO-0001` / `SWP-DEMO-0001` | 需确认编号规则（是否含日期、是否可枚举），影响接口契约 |
| **DQ-18** | **`swap_proposals` 的 `message` 长度上限？** 迭代一不做聊天（OOS-08） | `VARCHAR(500)`，仅发起说明 | 需确认 500 是否合适 |
| **DQ-19** | **是否需要「区域组」以支持后续跨区？** OOS-07 明确迭代一不做 | `trade_zones.parent_zone_id` 预留了层级 | 迭代 N 再评估 |
| **DQ-20** | **分类/成色字典是否需要排序权重以外的层级（父子分类）？** | 单层 + `sort_order` | 若需要二级分类，属范围外 |
| **DQ-21** | **`reports` 是否需要「举报处理结果」细分枚举？** | `status` = `PENDING/HANDLED/DISMISSED` + `handle_note` 文本 | 若需要「下架/警告/驳回」等结构化结论，需新增枚举值 |
| **DQ-22** | **管理员是否可能拥有交易身份？** P-00-A 规定管理员不参与交易 | `users.role` 单值枚举 `USER/ADMIN`，**无法同时是 ADMIN 与交易用户** | 当前设计使「管理员不得下单/发布」在数据层只是**约定**，需应用层拦截；已登记为对账/接口测试项 |
| **DQ-23** | **处罚 `ITEM_TAKEDOWN` 的 `ends_at` 语义是什么？** `ck_penalties_period` 要求 `ends_at > started_at`，故该类型也必须给 `ends_at` | 种子给了 `now()+1 day` 作为占位 | 商品下架本无「到期」概念，需确认：是设为「永久」还是复用某期限？**影响接口契约的必填参数** |
| **DQ-24** | **是否需要「同一商品历史被举报次数」的统计视图？** | 无视图，可用查询聚合 | 若管理员后台需要，属迭代二 |
| **DQ-25** | **是否需要为 `notifications` 增加「同事件去重键」？** | 无唯一约束 | 需确认「不重复发通知」（R-07/R-25）由应用层幂等保证还是数据库兜底 |

## 4. 需求文档中未覆盖、但建模必须落地的设计决策

> 这些是**需求基线未明确**、但领域模型必须做出的选择。已按最贴近需求语义的方式落地，登记备查。

| 编号 | 决策 | 落地方式 | 依据 / 理由 |
| --- | --- | --- | --- |
| DD-01 | 新增 `item_occupations` 占用台账表 | 独立表 + 部分唯一索引 | 任务步骤 1 明确列出「库存占用」实体；C-01/R-23 需要数据库级承载 |
| DD-02 | 「用户」与「个人资料」合并为 `users` | 单表 | 严格 1:1、无独立生命周期；减少无意义 JOIN |
| DD-03 | 多态引用（`item_occupations.ref_id`、`notifications.ref_id`）**不建外键** | 仅 `ref_type` + `ref_id` 列 + 索引 | PostgreSQL 无法对多态列建外键；由应用层保证引用有效性 |
| DD-04 | 新增 `idempotency_records` 幂等表 | 独立表（`user_id` + `idempotency_key` 唯一） | R-17 明确要求幂等键；E-06/E-16 需要请求体摘要 |
| DD-05 | 新增 `audit_logs` 审计表 | 独立表 + JSONB 前后状态 | R-34 要求治理动作留痕 |
| DD-06 | 订单取消原因独立为枚举 `order_cancel_reason` | `BUYER_CANCELLED` / `PAYMENT_TIMEOUT` / `ADMIN_TAKEDOWN` | 状态机 O-03/O-04/O-11 是三条不同路径，需可区分 |
| DD-07 | 交换终结原因独立为枚举 `swap_termination_reason` | 含 `VOID_ITEM_OCCUPIED` / `VOID_ITEM_OFF_SHELF` / `VOID_ITEM_BANNED` | R-24 整笔作废要求「说明作废原因」 |
| DD-08 | 处罚解封来源独立为枚举 `penalty_lift_source` | `SYSTEM_EXPIRY` / `APPEAL_APPROVED` / `ADMIN_MANUAL` | 状态机 P-04/P-05/P-07 三种解封路径需可审计 |
| DD-09 | 交换包物品行状态 `bundle_item_status` | `ACTIVE` / `RELEASED` / `COMPLETED` | SB-03 需要「进行中」概念；部分唯一索引依赖它 |
| DD-10 | 评价同时支持订单与交换（二选一 CHECK） | `order_id` 与 `swap_proposal_id` 互斥非空 | 评价状态机同时服务购买与交换完成 |
| DD-11 | 评价状态放在 `orders.review_status`（订单维度） | 枚举 `OPEN/BUYER_REVIEWED/...` | 状态机 §8 把互评状态定义为交易维度，而非单条评价维度 |
| DD-12 | 快照策略：`title_snapshot` / `price_snapshot` / `condition_snapshot` | 存文本/数值，不存外键 | R-13 要求商品后续编辑不影响历史订单与交换 |
| DD-13 | 金额统一 `numeric(12,2)` 且 `>= 0` | CHECK 约束 | R-13；避免浮点误差 |
| DD-14 | 时间统一 `timestamptz` | 全表 | R-19 服务端时间为准；A-20 时区 Asia/Shanghai |
| DD-15 | 字典表（分类/成色/区域/取货点）不用 ENUM 而用表 | 支持管理员维护与排序（Q-21） | ENUM 改文案成本高；字典需 `sort_order` / `is_active` |
| DD-16 | 12 张可并发写表加 `version` | `INTEGER NOT NULL DEFAULT 0` | R-18「乐观锁或条件更新」，禁止先查后改 |
| DD-17 | 为每个业务列加 `COMMENT ON COLUMN`（324 条） | 由列内联说明生成 | 让数据库自解释，`\d+` 即可查看；避免文档与库脱节 |
| DD-18 | 全表主键统一 `BIGINT GENERATED ALWAYS AS IDENTITY` | 不用 `SERIAL` | PG15 推荐写法；`ALWAYS` 防止应用层手工指定 ID |
| DD-19 | `citext` 用于 `username` / `email` | 扩展 + `UNIQUE` | FR-101 用户名唯一；避免 `Alice`/`alice` 并存导致登录歧义 |
