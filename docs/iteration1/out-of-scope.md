## 1. 使用说明

1. 本清单是迭代一**范围冻结的核心依据**：凡列入本清单的功能，迭代一**不设计接口、不建表、不写代码、不排期**。
2. 每项包含：**不做项**、**为什么不做**、**本迭代替代方案**、**未来迭代**（演进方向，仅备注，不承诺）。
3. 本清单共 **18 项**（≥ 验收要求的 11 项），其中 OOS-01、OOS-02、OOS-03、OOS-04 为**强制包含项**。
4. 需求评审时，任何「本迭代想做但未列入需求说明书 FR 编号」的想法，必须**先修改本清单与需求说明书**，否则不予实现。
5. 标记为【核心不做】的 4 项，是本迭代**最容易出现范围蔓延**的地方，评审时重点确认。

## 2. 强制不做项（验收要求必须包含）

### OOS-01 真实支付 【核心不做】

| 项 | 内容 |
| --- | --- |
| 不做 | 不接入微信支付、支付宝、银联、Apple Pay 等任何真实支付通道；不做支付回调、对账、退款、发票、资金流水 |
| 为什么不做 | 真实支付涉及商户资质、资金合规、对账与退款链路，工作量远超本迭代容量；且本迭代目标是打通流程与契约，不需要真实资金流 |
| 本迭代替代方案 | **模拟付款**：`POST /orders/{id}/mock-pay` 打标即视为付款成功，订单直接进入「已付款/待取货」。前端明确展示「模拟付款，不产生真实扣款」 |
| 影响 | 订单状态机保留 `PENDING_PAYMENT → PAID` 转换，未来接入真实支付时**不改状态机，只改触发来源** |
| 未来迭代 | 迭代 N：接入单一支付通道（建议先微信小程序支付），增加支付流水表与回调幂等处理 |

### OOS-02 多人交换链 【核心不做】

| 项 | 内容 |
| --- | --- |
| 不做 | 不做 A→B→C 的链式交换、不做循环交换（A 的物给 B、B 的给 C、C 的给 A）、不做三人及以上共同参与的撮合 |
| 为什么不做 | 多人交换链需要撮合算法、多方一致性协议与超时协调，且失败回滚复杂（任一环退出则整链作废），属于典型「高复杂度、低验证价值」功能 |
| 本迭代替代方案 | 仅支持**一对一交换**：一个交换包 ↔ 一个目标用户的一件或多件商品。多方需求通过**拆成多笔独立的一对一交换**自行完成 |
| 影响 | `SwapProposal` 恰好两个参与方（proposer / target），数据模型无需多方参与表 |
| 未来迭代 | 迭代 N：引入交换链撮合（需先冻结多方一致性协议） |

### OOS-03 现金补差价 【核心不做】

| 项 | 内容 |
| --- | --- |
| 不做 | 交换时双方估价不等价，**不支持**一方用现金/余额/积分补足差额；不做差额计算、不做差额支付、不做差额退款 |
| 为什么不做 | 补差价需要真实资金能力（与 OOS-01 冲突），且会引入纠纷判定与资金纠纷处理，超出治理能力 |
| 本迭代替代方案 | 交换包展示**估价合计**，仅供双方参考；是否「划算」由用户线下自行判断，平台**不做等价判定、不做强制**。用户可通过增减包内物品自行调整合计值 |
| 影响 | 交换提议不产生任何金额字段的支付语义；`SwapBundle.estimatedTotal` 为纯展示字段 |
| 未来迭代 | 迭代 N：若接入真实支付，可考虑「差额支付」，但需先具备纠纷仲裁能力 |

### OOS-04 部分接受交换包 【核心不做】

| 项 | 内容 |
| --- | --- |
| 不做 | 目标方**不能**只接受交换包中的部分物品；不能挑出包内某几件成交、不能对包内物品逐件接受/拒绝 |
| 为什么不做 | 部分接受会使「占用与释放」变成物品级细粒度问题，与「整笔作废」规则冲突，状态组合爆炸，测试成本极高 |
| 本迭代替代方案 | **整包接受或整包拒绝**（all-or-nothing）。若目标方只想要部分物品，正确做法是**拒绝原提议并发起反提案**，在反提案中给出自己想要的组合 |
| 影响 | 交换接受接口作用于**整笔提议**，不存在 item 级接受参数；接受成功后一次性占用包内全部物品 |
| 未来迭代 | 迭代 N：若引入部分接受，必须重新设计占用模型（物品级锁）与作废规则 |

## 3. 地理、隐私与定位

### OOS-05 定位与住址

| 项 | 内容 |
| --- | --- |
| 不做 | 不调用浏览器 Geolocation、不读 GPS、不做 IP 定位；不采集、不填写、不存储、不展示任何住址/门牌号/宿舍楼栋号 |
| 为什么不做 | 校园场景下定位精度不足以定位到取货点；采集住址带来隐私合规风险与用户抵触，且与「公共取货点交付」模型无关 |
| 本迭代替代方案 | 用户从**预设交易区域列表**手动勾选 1–5 个常用区域；交付地点统一使用**公共取货点** |
| 未来迭代 | 迭代 N：可考虑「仅在用户主动点击时申请一次定位，用于推荐交易区域」，仍需用户显式同意 |

### OOS-06 地图与导航

| 项 | 内容 |
| --- | --- |
| 不做 | 不集成地图 SDK/瓦片服务、不展示地图、不画路线、不做导航跳转、不做距离计算与「附近」排序 |
| 为什么不做 | 取货点是校内标志性建筑门口，文字描述已足够；地图集成引入第三方依赖、密钥管理与成本 |
| 本迭代替代方案 | 取货点以「**名称 + 归属交易区域 + 文字说明**」展示（如「图书馆正门台阶右侧」） |
| 未来迭代 | 迭代 N：可加静态示意图或跳转第三方地图（只跳转，不自建） |

### OOS-07 跨区取货与跨区交易

| 项 | 内容 |
| --- | --- |
| 不做 | 不支持下单或交换的取货点跨越不同交易区域；不支持跨校区、跨城市的商品交易 |
| 为什么不做 | 迭代一只服务 2–3 个校区及周边社区，跨区交易破坏「同区域当面交付」的信任前提 |
| 本迭代替代方案 | 交易区域在**浏览阶段即可过滤**；下单/发起交换时强校验「商品区域 = 取货点区域 = 订单区域」，不一致直接拒绝 |
| 未来迭代 | 迭代 N：若多校区运营成熟，可引入「区域组」概念支持相邻区域互通 |

## 4. 交互与沟通

### OOS-08 站内聊天与私信

| 项 | 内容 |
| --- | --- |
| 不做 | 不做一对一聊天、不做群聊、不做图片消息、不做消息已读回执、不做基于聊天的议价 |
| 为什么不做 | 即时通讯涉及连接管理、消息存储、内容审核与合规，是独立产品级工程；本迭代无信息审核能力承载其风险 |
| 本迭代替代方案 | 全流程**结构化交互**：订单/交换提议本身承载状态沟通；系统在关键节点下发**站内通知**（下单、付款、交付、确认、交换提议、处罚） |
| 未来迭代 | 迭代 N：如必须沟通，优先做「受限留言」（订单内固定场景留言，带审核与限流），而非通用 IM |

### OOS-09 推荐算法与个性化排序

| 项 | 内容 |
| --- | --- |
| 不做 | 不做协同过滤、不做用户画像、不做千人千面推荐、不做竞价排序、不做「猜你喜欢」 |
| 为什么不做 | 迭代一商品量与用户量不足以训练有效模型；排序不可解释会引发公平性质疑 |
| 本迭代替代方案 | 固定可解释排序：**分类筛选 + 状态筛选 + 发布时间倒序**（可选估价区间过滤）。排序规则在接口清单中冻结 |
| 未来迭代 | 迭代 N：可先做规则型「同区域优先 + 新鲜度加权」，暂不做模型 |

### OOS-10 复杂议价

| 项 | 内容 |
| --- | --- |
| 不做 | 不做砍价、不做阶梯价、不做优惠券、不做议价申请与还价流程、不做「接受报价」功能 |
| 为什么不做 | 与「估价仅为展示、平台不定价」的模型冲突，且议价需要聊天或多次往来的状态承载 |
| 本迭代替代方案 | 购买路径**一口价**（按估价直接下单）；交换路径通过**交换包与一轮反提案**间接表达「价值协商」 |
| 未来迭代 | 迭代 N：若要做议价，需先有 OOS-08 的受限留言能力 |

## 5. 账号与权限

### OOS-11 第三方登录与账号绑定

| 项 | 内容 |
| --- | --- |
| 不做 | 不做微信/QQ/校园统一身份认证（CAS）登录，不做手机验证码登录，不做账号绑定与解绑 |
| 为什么不做 | 需要对接外部平台的资质、回调与用户信息授权，且校园统一认证需校方配合，周期不可控 |
| 本迭代替代方案 | **账号密码注册登录**（用户名/邮箱 + 密码），令牌制登录态保持 |
| 未来迭代 | 迭代 N：优先对接校园统一身份认证（更契合校园场景），其次微信登录 |

### OOS-12 多管理员角色与细粒度 RBAC

| 项 | 内容 |
| --- | --- |
| 不做 | 不做「超级管理员/审核员/客服」等细分管理员角色，不做按区域划分管理员管辖范围，不做可配置权限点 |
| 为什么不做 | 迭代一管理员人数极少、治理动作固定，细粒度 RBAC 是过度设计 |
| 本迭代替代方案 | **单一管理员角色（ROLE_ADMIN）**，拥有治理动作全集；所有治理动作强制记录操作者与理由，为未来审计留痕 |
| 未来迭代 | 迭代 N：引入「审核员（仅可下架/处理申诉）+ 超级管理员（可封禁）」二级模型 |

### OOS-13 用户注销与数据导出

| 项 | 内容 |
| --- | --- |
| 不做 | 不做账号自助注销、不做数据导出、不做账号合并 |
| 为什么不做 | 涉及历史订单与处罚记录的保留义务，需要法务与数据保留策略；迭代一无此策略 |
| 本迭代替代方案 | 用户可**下架全部商品并停止使用**；如需删除账号，由管理员线下处理并记录在处罚/审计记录中 |
| 未来迭代 | 迭代 N：按合规要求实现「注销 + 匿名化 + 保留交易凭证」 |

## 6. 交易与售后

### OOS-14 退款与售后仲裁

| 项 | 内容 |
| --- | --- |
| 不做 | 不做退款、不做退货、不做售后工单、不做资金仲裁、不做赔付 |
| 为什么不做 | 本迭代无真实资金（OOS-01），无资金即无退款；线下当面交付已让用户在交付时完成验货 |
| 本迭代替代方案 | 交付环节**当面验货**：买家不满意可**拒绝确认收货**；同时提供**举报**与**管理员介入**（下架商品、封禁违规用户）。已确认收货的订单不可撤销 |
| 未来迭代 | 迭代 N：接入真实支付后，同步设计退款与仲裁流程 |

### OOS-15 发票与税务

| 项 | 内容 |
| --- | --- |
| 不做 | 不开具发票、不做电子发票、不做税务对接 |
| 为什么不做 | 个人闲置物品转让非经营性销售，本迭代无资金流，无开票主体 |
| 本迭代替代方案 | 订单详情仅展示**估价快照与交易记录**，明确标注「非经营性交易，不提供发票」 |
| 未来迭代 | 迭代 N：若引入商家/机构卖家，再评估 |

### OOS-16 物流与快递

| 项 | 内容 |
| --- | --- |
| 不做 | 不对接快递、不做运单号、不做寄件、不做运费计算 |
| 为什么不做 | 平台定位是同区域当面交付，物流会引入地址（与 OOS-05 冲突）与运费分摊问题 |
| 本迭代替代方案 | 公共取货点**当面交付**，卖家标记交付、买家确认收货 |
| 未来迭代 | 迭代 N：如扩区域，需重新评估交付模型 |

## 7. 工程与运维

### OOS-17 生产级部署与运维体系

| 项 | 内容 |
| --- | --- |
| 不做 | 不做生产级高可用、不做容器编排（K8s）、不做灰度发布、不做全链路监控告警、不做压测与容量规划、不做容灾备份策略 |
| 为什么不做 | 迭代一交付物是「**能启动的工程骨架**」，不是可上线系统；业务逻辑尚未实现，运维投入无收益 |
| 本迭代替代方案 | 本地开发环境可启动（后端 Spring Boot 2.7.18 + PostgreSQL 15 + 前端 Vue3/TS 开发服务器）；配置外置为配置文件/环境变量；日志输出到控制台与文件 |
| 未来迭代 | 迭代 N：容器化 + CI/CD + 监控告警 + 备份 |

### OOS-18 文件对象存储与 CDN

| 项 | 内容 |
| --- | --- |
| 不做 | 不对接 OSS/S3 等云对象存储，不做 CDN 加速、不做图片动态裁剪与水印 |
| 为什么不做 | 迭代一无真实流量，本地文件存储足够验证上传与展示链路；引入云存储需要账号与密钥管理 |
| 本迭代替代方案 | 图片**存储于服务端本地目录**，通过统一静态资源路径访问；仅做**格式与大小校验**（JPG/PNG/WebP，单张 ≤5MB） |
| 未来迭代 | 迭代 N：切换对象存储（接口抽象为 `FileStorageService`，便于替换） |
